# Investigation: GM Agent Narrative Focus and Combat Output Separation

## Summary
The GM spawns enemies too early because gameplay enablement currently acts as combat initiation: gameplay-enabled location-room ticks route directly to the gameplay coordinator, and the gameplay coordinator creates an encounter whenever none exists after only basic participant guardrails. Internal narrative/gameplay state is mostly separated, but public presentation still mixes narrative prose, combat actions, GM outcomes, and roll summaries in one message stream.

## Symptoms
- GM agent needs to focus primarily on story development before spawning enemies.
- Narrative outputs and combat outputs are currently not sufficiently separated.

## Background / Prior Research
No external research required at kickoff; investigation is focused on workspace code and existing GM/location-room behavior.

### Pair Investigation - Tick Routing, Combat Creation, and Public Output Separation (2026-05-24)

#### Verdict by hypothesis
1. **Confirmed:** Gameplay-enabled/allowlisted room ticks bypass the normal story-first narrative coordinator path and route directly to gameplay turn processing. The gameplay path still requires narrative mode/GM configuration, but it does not run `narrativeCoordinator.processTurn` first.
2. **Confirmed with guardrails:** If no active encounter exists, the gameplay coordinator immediately asks the GM gameplay generator for an encounter proposal, normalizes monsters/enemies, creates an active encounter, and appends setup/action/outcome public messages. It skips only when fewer than two living/playable participants remain.
3. **Confirmed:** Narrative/gameplay prompt contracts do not include a structured “story first / combat readiness / spawn encounter?” gate. Narrative beats have continuity/objective/thread fields; gameplay proposal prompts directly request encounter fields.
4. **Partially confirmed / refined:** Public room output uses one public message stream, with gameplay classification and rolls projected from metadata. Current code exposes sanitized `gameplayRolls` in addition to `gameplayMessageKind` and a separate `gameplay` summary object, so separation is no longer *only* a kind flag. However narrative prose, character combat actions, GM combat outcomes, and human-readable roll summaries still live in the same `messages[]` stream and `content` field.
5. **Confirmed:** Existing tests explicitly encode the current immediate-gameplay behavior, including gameplay routing before narrative, active-run creation on manual initiation, immediate manual processing, and a three-message combat transcript (`gm_setup`, `character_action`, `gm_outcome`).

#### Evidence
- **Tick API and feature flag flow:** The manual tick route authenticates, derives `actor`, and delegates directly to `locationRoomService.requestTickAndProcess(locationId, { actor, walletAddress })`; the route mostly maps service errors afterward (`app/api/eliza/location-rooms/[locationId]/tick/route.ts:20-31`, `app/api/eliza/location-rooms/[locationId]/tick/route.ts:33-81`). Gameplay enablement is global flag + location allowlist (`lib/eliza/locationRooms/service.ts:299-307`), configured from `ELIZA_LOCATION_ROOM_GAMEPLAY_ENABLED` and allowlist/location-id env vars (`lib/eliza/config.ts:271-276`). Gameplay mode also requires narrative mode to be enabled (`lib/eliza/locationRooms/service.ts:345-347`).
- **Manual gameplay initiation creates/reuses an active run:** During manual validation/enqueue, gameplay-enabled rooms call `createOrReuseActiveRun` and enqueue the tick with that run id (`lib/eliza/locationRooms/service.ts:573-591`). Tests assert allowlisted gameplay rooms return a `gameplayRun` and enqueue with `gameplayRunId: 'run-1'` (`tests/api/eliza/location-room-service.test.ts:906-943`) and reuse the active run on repeated initiation (`tests/api/eliza/location-room-service.test.ts:952-973`).

The narrative coordinator branch starts only later (`lib/eliza/locationRooms/service.ts:1103-1104`). Failure bookkeeping follows the same split: gameplay-enabled rooms mark gameplay turns failed; only non-gameplay narrative rooms mark narrative beats failed (`lib/eliza/locationRooms/service.ts:964-985`). A dedicated test is named “runs an allowlisted gameplay tick through the gameplay coordinator before narrative mode” and asserts `narrativeCoordinator.processTurn` is not called (`tests/api/eliza/location-room-service.test.ts:1201-1241`).
- **Immediate encounter/enemy creation:** Gameplay coordinator looks up an existing turn/active encounter (`lib/eliza/locationRooms/gameplay/coordinator.ts:373-375`), clears a non-active encounter when no turn is being retried (`lib/eliza/locationRooms/gameplay/coordinator.ts:379-381`), and if none exists, only checks for at least two playable participants before generating a proposal (`lib/eliza/locationRooms/gameplay/coordinator.ts:383-393`). It also stores all public message ids on the completed gameplay turn (`lib/eliza/locationRooms/gameplay/coordinator.ts:785-787`).
- **Prompts/contracts lack a story-first gate:** The narrative beat contract contains `publicNarration`, `speakerInstruction`, `stateSummary`, `currentObjective`, `openThreads`, featured tokens, and selected speaker, with rules requiring only speaker instruction/state summary and eligible token ids (`lib/eliza/locationRooms/gameMasterGenerator.ts:254-265`). The gameplay encounter contract directly requests encounter title/summary/setup narration, difficulty, monster count/name/archetype, HP/AC/attack/damage, scene DC, XP, boons, rewards, and victory text (`lib/eliza/locationRooms/gameplay/gameMasterGameplayGenerator.ts:426-439`). Outcome narration only asks for public narration and continuity updates (`lib/eliza/locationRooms/gameplay/gameMasterGameplayGenerator.ts:474-479`). No prompt field or parser result represents `combatReady`, `spawnEncounter`, `storyPhase`, or similar.

Route test “manual tick processes owner requests immediately when the room tick is claimed” expects status 200 and `processing: { attempted: true, status: 'completed' }` with a `gameplayRun` in the payload (`tests/api/eliza/location-room-routes.test.ts:243-277`). Service tests cover immediate manual enqueue/process without draining follow-up turns (`tests/api/eliza/location-room-service.test.ts:687-735`) and public gameplay summary/message classification without raw private metadata (`tests/api/eliza/location-room-service.test.ts:375-480`).

#### Eliminated or narrowed hypotheses
- Gameplay mode is **not** enabled by narrative mode alone; it requires the global gameplay flag and a matching location allowlist (`lib/eliza/locationRooms/service.ts:299-307`).
- Gameplay mode is **not** independent from narrative configuration; gameplay-enabled rooms require narrative mode and a resolvable GM agent (`lib/eliza/locationRooms/service.ts:345-353`).
- The public API does **not** expose raw private mechanics wholesale; tests assert private fields like `privateInstruction`, `diceResults`, `privateDc`, `roundsActed`, `damageDealt`, `performanceScore`, and `lineItems` are absent (`tests/api/eliza/location-room-service.test.ts:479-487`). Current DTO projection additionally sanitizes `publicRolls` into public `gameplayRolls` (`lib/eliza/locationRooms/service.ts:185-199`).
- Combat creation is not unconditional for every gameplay tick: existing active encounters are reused, terminal/non-active encounters are skipped when appropriate, and ticks skip if fewer than two playable participants remain (`lib/eliza/locationRooms/gameplay/coordinator.ts:373-390`, `lib/eliza/locationRooms/gameplay/coordinator.ts:456-460`).

#### Recommendations
1. Add an explicit **story-first readiness gate** before `generateEncounterProposal`: e.g. `narrativeCoordinator.planBeat` or a new GM decision contract returning `{ publicNarration, speakerInstruction, stateAfter, combatReadiness, encounterSeed? }`, where gameplay encounter creation only occurs when `combatReadiness === 'ready'` or similar.
2. Split public presentation into first-class domains: keep `messages[]` for story chat, but add either `combatLog[]` or stronger public message domains (`narrative`, `combat_setup`, `combat_action`, `combat_outcome`, `system_roll`) so clients can render/hide combat separately without parsing metadata.
3. Stop appending roll summaries into prose `content`; rely on `gameplayRolls`/structured combat log for dice/mechanics and reserve GM outcome `content` for narrative-only prose.
4. Update tests to encode desired story-first behavior: gameplay-enabled first tick should run/record a narrative beat and only create encounters after the readiness gate says combat is appropriate. Keep existing immediate-combat tests as legacy/regression fixtures only if preserving backwards compatibility is required.
5. Preserve current safety constraints: keep public roll sanitization and private mechanics redaction tests while adding assertions that narrative and combat surfaces remain independently renderable.

## Root Cause
The root cause is orchestration-level coupling between “gameplay enabled” and “combat encounter should begin.” In `lib/eliza/locationRooms/service.ts:1044-1049`, gameplay-enabled locations are routed directly into `gameplayCoordinator.processTurn(...)` before the narrative coordinator path is considered; the narrative branch starts later at `lib/eliza/locationRooms/service.ts:1103-1104`. Once inside `lib/eliza/locationRooms/gameplay/coordinator.ts:383-423`, the gameplay coordinator treats absence of an active encounter as a reason to generate and create one, after checking only that enough living/playable participants exist.

The resulting flow is: gameplay-enabled tick → gameplay coordinator → no active encounter → generate encounter proposal → create active encounter → append combat setup/action/outcome messages. There is no story-first gate for narrative maturity, objective completion, unresolved story threads, escalation phase, explicit combat trigger, or GM combat-readiness.

Prompt wording contributes but is secondary. The narrative GM contract in `lib/eliza/locationRooms/gameMasterGenerator.ts:254-265` lacks structured story-phase or combat-readiness fields. The gameplay encounter prompt in `lib/eliza/locationRooms/gameplay/gameMasterGameplayGenerator.ts:426-439` directly requests monster/encounter fields, but that prompt is called only after orchestration has already decided to start combat.

Public output separation is also incomplete. Stored room messages have one `content` plus `metadata` shape (`lib/eliza/locationRooms/types.ts:24-37`), and public projection adds `gameplayMessageKind` / `gameplayRolls` while preserving one `content` stream (`lib/eliza/locationRooms/service.ts:185-199`). Gameplay outcomes currently append roll-summary text into GM narration before insertion into that stream (`lib/eliza/locationRooms/gameplay/coordinator.ts:725-768`).

## Recommendations
1. Add a story-first turn selector in `lib/eliza/locationRooms/service.ts` so gameplay-enabled does not automatically mean combat. Suggested modes: `narrative`, `threat_building`, `combat`, `aftermath`. No active encounter and no explicit combat trigger should route to narrative; active encounters should route to gameplay; terminal encounters should return to aftermath/narrative.
2. Stop manual gameplay ticks from implicitly creating/reusing gameplay runs in `lib/eliza/locationRooms/service.ts`. Add an explicit request mode such as `auto | narrative | combat`; only create/reuse gameplay runs for active encounters, explicit combat mode, or a narrative GM escalation request.
3. Gate encounter creation in `lib/eliza/locationRooms/gameplay/coordinator.ts` before `generateEncounterProposal()`. Require an explicit signal such as `allowCreateEncounter`, `encounterTrigger`, `narrativeBeatId`, and/or `encounterSeed`; otherwise return/defer with a reason like `no_combat_trigger`.
4. Expand the narrative GM beat contract in `lib/eliza/locationRooms/gameMasterGenerator.ts` with structured fields such as `beatType`, `combatReadiness`, `requestedGameplayAction`, and `encounterSeed`. Store initially in beat metadata if avoiding schema changes is preferable.
5. Use the existing `speakerInstruction` seam in `lib/eliza/locationRooms/gameplay/actionGenerator.ts` / gameplay coordinator so combat that follows a narrative beat preserves story intent.
6. Separate prose narration from mechanics in `lib/eliza/locationRooms/gameplay/coordinator.ts`: keep message `content` as narrative prose and rely on `gameplayRolls` / metadata or a combat log for dice and mechanics.
7. Add first-class public message domains/kinds in `lib/eliza/locationRooms/types.ts`, `service.ts`, and potentially `repository.ts`, e.g. `domain: narrative | gameplay | system` and `messageKind: gm_beat | character_utterance | gm_setup | character_action | gm_outcome | roll_summary`.
8. Update tests that currently encode immediate-combat behavior, especially `tests/api/eliza/location-room-service.test.ts`, `tests/api/eliza/location-room-routes.test.ts`, `tests/lib/eliza/location-room-gameplay-coordinator.test.ts`, `tests/lib/eliza/location-room-game-master-generator.test.ts`, `tests/lib/eliza/location-room-gameplay-generators.test.ts`, and `tests/lib/eliza/location-room-gameplay-public-rolls.test.ts`.

## Rollout Note
Gameplay-enabled rooms no longer auto-start combat. This behavior change intentionally addresses the root cause above: “gameplay enabled” had been coupled to “begin a combat encounter,” causing ticks to bypass story-first narrative beats and create encounters without an explicit combat trigger.

## Preventive Measures
- Add routing tests proving gameplay-enabled rooms with no active encounter and no combat trigger process a narrative beat instead of creating an encounter.
- Add gameplay coordinator tests proving `generateEncounterProposal()` is not called unless an explicit encounter trigger is present.
- Add prompt contract tests requiring story-first rules and structured combat-readiness fields in the narrative GM prompt.
- Add public API separation tests asserting narrative and gameplay messages have distinct domains/kinds, and roll summaries are not appended to prose `content`.
- Preserve existing redaction/sanitization tests so raw mechanics, private instructions, reward internals, and private metadata remain hidden.
- Document turn-mode semantics for narrative ticks, threat-building beats, combat triggers, active encounter continuation, and aftermath return.
- Store auditable combat-initiation metadata such as `triggerSource`, `narrativeBeatId`, `combatReadiness`, `requestedByActor`, and `encounterSeed`.
