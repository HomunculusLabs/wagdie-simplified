# Investigation: Searing Uses Original Metadata After Character Updates

## Summary
Searing generation currently reads live DB `wagdie_characters.metadata`, but the resolver uses only root NFT-style `metadata.attributes` to select static WAGDIE layer PNGs. Normal character edits, AI persona edits, image URL updates, and searing read-model writes do not update those root attributes, so searing can appear to use original/static metadata even though it is reading the DB.

## Symptoms
- A character can have updated metadata and/or image in the app/database.
- When searing runs, the generated seared image appears to use the original metadata/layers rather than the updated metadata/image.
- Need to determine whether preview, sync/materialization, layer resolution, composer input, storage, or display caching is responsible.

## Background / Prior Research
- Existing historical report `docs/investigations/searing-image-generation-2026-05-08.md` established that searing image generation is an off-chain materialization path, not just chain event indexing.
- The same report documented that materialization resolves layers from the character read model, composes a PNG, uploads it, and updates character metadata/read-model fields; current behavior must be re-verified against code.

### 2026-05-28 - Searing preview/materialization metadata-source trace

#### Executive finding
Searing preview and sync/materialization do **not** compose from `wagdie_characters.image_url`, `metadata.image`, `metadata.searImage`, prior `searing_events.seared_image_url`, or the frontend display candidate list. Both generation paths resolve layer PNGs strictly from the current row's root `metadata.attributes` array plus the selected concord searing map, then compose those layer URLs. If a character edit changes only display/read-model fields (`name`, stats, `background_story`, AI persona, `image_url`, `metadata.image`, `metadata.searImage`, etc.) and does not change root `metadata.attributes`, searing will still use the original/static NFT trait layers.

#### 1. Preview flow: route -> character fetch -> resolver -> composer
- Preview route parses `tokenId` and `concordId`, then fetches exactly `token_id, metadata` from `CHARACTERS_TABLE`; `image_url` is not selected and therefore cannot affect preview composition at this entrypoint (`app/api/characters/[tokenId]/searing/preview/route.ts:23-47`).
- The fetched `character.metadata` is passed directly to `resolveSearingLayersForCharacter(character.metadata, concord)`, then `resolution.layers` is passed directly to `searingImageComposer.compose(...)`; the PNG response uses only the composed image and variant headers (`app/api/characters/[tokenId]/searing/preview/route.ts:64-75`).
- The resolver normalizes only NFT-style attributes. It accepts either an attributes array or `metadata.attributes`; otherwise it returns an empty attribute list (`lib/domain/searing/searing-layer-resolver.ts:66-75`). It derives alignment from those attributes (`lib/domain/searing/searing-layer-resolver.ts:80-96`) and chooses the concord variant from that alignment (`lib/domain/searing/searing-layer-resolver.ts:125-158`).
- Layer URLs are built from attribute `trait_type`/`value` for the fixed composable layer set plus a searing overlay for the concord's resolved location/new trait (`lib/domain/searing/searing-layer-resolver.ts:160-216`). There is no read of `metadata.image`, `metadata.searImage`, `metadata.searing_materialization`, or `image_url` in the resolver.
- The composer consumes only the resolved `SearingLayer[]`: it maps `layers` to `layer.url`, downloads/reads those layer PNGs, composites them, and returns `{ image, layerUrls }` (`lib/services/searing-image-composer.ts:124-146`). There is no input parameter for a source character image URL or previous seared image.
- Frontend preview components only construct an `<img src="/api/characters/{id}/searing/preview?concordId=...">`; they do not send image metadata to the preview route (`components/characters/searing/SearingPreview.tsx:14-22`, `components/characters/searing/SearingPreview.tsx:37-52`). The searing page's result panel similarly uses that preview endpoint until materialization completes (`components/searing/SearingPageClient.tsx:124-131`).

#### 2. Sync/materialization flow and what can influence composition
- Public sync route delegates to `searingMaterializationService.verifyTransactionAndMaterialize({ tokenId, transactionHash, retryFailed, repairCompleted })`; it does not fetch or send character image fields itself (`app/api/characters/[tokenId]/searing/sync/route.ts:34-55`). Batch sync likewise delegates to `materializePendingBatch(...)` (`app/api/sync/searing/route.ts:80-87`).
- Transaction sync inserts/loads a searing event from decoded chain logs, then calls `materializeEvent(event.id)` (`lib/services/searing-materialization-service.ts:276-342`). Existing completed events with cache-safe versioned image URLs can short-circuit before composition unless repair is requested (`lib/services/searing-materialization-service.ts:190-244`).
- For a claimed event, materialization fetches the character via `this.characters.findCharacter(event.token_id)` and the concord map via `findByConcordTokenId(...)` (`lib/services/searing-materialization-service.ts:428-436`). The repository selection for this fetch is `token_id, metadata, image_url, infection_status, infected` (`lib/repositories/character-materialization-repository.ts:126-136`).
- Despite selecting `image_url`, composition still uses only `character.metadata`: `resolveSearingLayersForCharacter(character.metadata, concord)` -> `this.composer.compose(resolution.layers)` -> `uploadSearedImage(...)` (`lib/services/searing-materialization-service.ts:439-445`). Thus `image_url`, `metadata.image`, `metadata.searImage`, and prior materialized image URLs do not feed the resolver/composer.
- `image_url`/infected image fields influence only the post-composition read-model update. `getInfectedImageUrl()` inspects `metadata.infectedImage`, `metadata.infected_image_url`, nested infection image fields, `metadata.image`, and `character.image_url` for infected-image preservation (`lib/repositories/character-materialization-repository.ts:71-87`). `shouldPreserveCurrentImage()` uses infection state flags (`lib/repositories/character-materialization-repository.ts:89-95`). `nextImageUrl` is then either an infected/current preserved image or the newly uploaded `update.searedImageUrl` (`lib/repositories/character-materialization-repository.ts:145-151`). This happens **after** composition.
- `buildUpdatedMetadata()` spreads existing metadata and writes top-level read-model/display fields: `image`, `isSeared`, `searImage`, nested `searedConcord`, and `searing_materialization.seared_image_url` (`lib/repositories/character-materialization-repository.ts:97-121`). It does not assign root `metadata.attributes`; existing root attributes are preserved unchanged by `...existing`.
- The read-model update writes exactly `metadata: nextMetadata`, `image_url: nextImageUrl`, and `updated_at` back to `wagdie_characters` (`lib/repositories/character-materialization-repository.ts:153-158`). It also marks `character_concords` seared separately (`lib/repositories/character-materialization-repository.ts:201-246`).
- The event completion stores the uploaded `seared_image_url` and materialization metadata including `layers` and `layer_urls` in `searing_events`, but that is an event record, not resolver input for the current composition (`lib/services/searing-materialization-service.ts:463-477`; repository update at `lib/repositories/searing-event-repository.ts:204-220`).
- Tests encode the same behavior: materialization test stubs `findCharacter` as `{ token_id: 5873, metadata }`, uses real resolver/composer, uploads a versioned image, and asserts a visible pixel change (`tests/unit/searing-materialization-service.test.ts:41-129`). The legacy-completed URL test proves prior deterministic completed images are treated as `completed_without_image` unless repair is requested, not as composition inputs (`tests/unit/searing-materialization-service.test.ts:131-160`).

#### 3. Character update/edit flows and whether they update root `metadata.attributes`
- Normal character sheet editor initializes and saves DB-column/read-model fields, not root NFT metadata traits. The editor state is `name`, `story`, core stats, derived stats, and level/experience (`hooks/useCharacterEditor.ts:31-39`), initialized from DB columns with metadata only as fallback (`hooks/useCharacterEditor.ts:91-119`). Save builds a diff for `name`, `background_story`, stats, hp/ac/speed, level, and experience (`lib/domain/character/update-diff.ts:9-44`) and PATCHes `/api/characters/{tokenId}` (`hooks/useCharacterSave.ts:55-78`).
- The PATCH handler allow-list is only `background_story`, `equipment`, `name`, stats, hp/ac/speed, level, and experience; `metadata`, `metadata.attributes`, `image_url`, `metadata.image`, and searing fields are not accepted (`lib/api/handlers/character-update.ts:26-31`, `lib/api/handlers/character-update.ts:95-110`). The repository writes exactly the filtered update object to the character row (`lib/repositories/character/character-query-repository.ts:454-488`).
- Both `/api/characters/[tokenId]` and the singular compatibility route `/api/character/[tokenId]` use the same shared PATCH handler (`app/api/characters/[tokenId]/route.ts:22-28`; `app/api/character/[tokenId]/route.ts:23-29`).
- AI persona editor updates Eliza character records, not `wagdie_characters`. The UI calls `saveAICharacter(updateData)` (`components/characters/ai-editor/AIPersonaTab.tsx:115-126`), which PUTs to `/api/eliza/characters/{tokenId}` (`hooks/useAICharacter.ts:95-105`). The route validates the AI-character payload and either `replaceRecord(...)` or `createRecord(...)` in the Eliza character store (`app/api/eliza/characters/[tokenId]/route.ts:80-218`). The mapped fields are persona fields such as username, backstory, bio/lore/topics, style, examples, templates, settings (`hooks/useAIPersonaEditor.ts:508-548`; `lib/eliza/agent-character-mapper.ts:157-217`, `lib/eliza/agent-character-mapper.ts:260-276`). No `wagdie_characters.metadata` or `image_url` write occurs in this route.
- AI persona import similarly normalizes an Eliza export, merges it into the existing Eliza agent character, and calls `client.characters.replaceRecord(...)`; it does not update `wagdie_characters` (`app/api/eliza/characters/[tokenId]/import/route.ts:103-138`).
- Persona assistant route only authorizes, validates, and returns a proposal from `runPersonaAssistant(...)`; it does not persist character metadata itself (`app/api/eliza/characters/[tokenId]/persona-assistant/route.ts:46-89`).
- Static metadata route is GET-only. It reads `public/metadata/characters/{tokenId}.json`, optionally overrides response `image` with hosted `/images/characters/{tokenId}.png?v=metadata-20260509`, deletes `animation_url`, and returns JSON with cache headers (`app/api/characters/metadata/[tokenId]/route.ts:30-83`). It does not read or update `wagdie_characters` and therefore cannot change root `metadata.attributes`.
- Other non-route scripts can write metadata/images. Initial/import migration writes raw metadata wholesale, including original `attributes`, into `wagdie_characters.metadata` (`scripts/generate_migration.py:136-145`). `scripts/import-gcs-images.ts` merges existing metadata with sidecar metadata and can overwrite root attributes if the sidecar contains `attributes`; it also updates `image_url` when the imported image URL differs (`scripts/import-gcs-images.ts:155-180`, `scripts/import-gcs-images.ts:307-317`). `scripts/point-images-to-local.ts` only updates `metadata.image`/`metadata.asset_import` and preserves all other metadata fields, including attributes (`scripts/point-images-to-local.ts:71-75`, `scripts/point-images-to-local.ts:108-130`).

#### 4. Frontend display/caching vs generation source
- Display source ordering is separate from generation source. `getCharacterImageCandidates()` orders infected dynamic images first, then seared materialization/legacy seared candidates, then local static image, then placeholder (`lib/utils/image.ts:147-198`, `lib/utils/image.ts:215-236`). This is used by character cards/detail/searing UI (`components/characters/CharacterCard.tsx:23-35`; `hooks/useCharacterImageDisplay.ts:25-56`; `components/searing/SearingPageClient.tsx:53-67`).
- Seared display candidates are ordered as `metadata.searing_materialization.seared_image_url`, then `metadata.searImage`, then DB `image_url`; only if those materialized candidates exist are `metadata.image_url` and `metadata.image` appended as fallback candidates (`lib/utils/image.ts:175-194`). Tests confirm materialized image precedes legacy `searImage` and local static image, DB `image_url` is used as a seared candidate only when metadata indicates seared, and original `metadata.image` is not promoted merely by `isSeared` (`tests/unit/image.test.ts:25-51`).
- Infected display can hide the seared image as primary without changing generation. Tests confirm infected image remains primary while seared image is still exposed in disclosure (`tests/unit/image.test.ts:13-23`, `tests/unit/image.test.ts:53-70`). The searing page separately detects when a completed seared image is hidden by infection (`components/searing/SearingPageClient.tsx:286-299`).
- The searing page's textual preview of resolved trait uses the same attribute-only resolver helpers (`normalizeNftAttributes(character.metadata)` -> `getAlignmentForAttributes(...)` -> `resolveSearingVariant(...)`) for UI labels (`components/searing/SearingPageClient.tsx:132-134`); this mirrors, but does not replace, server generation.

#### Eliminated hypotheses
- **`image_url` drives preview generation:** eliminated. Preview route selects only `token_id, metadata` (`app/api/characters/[tokenId]/searing/preview/route.ts:41-47`) and composer accepts only resolved layer URLs (`lib/services/searing-image-composer.ts:124-146`).
- **`metadata.image` or updated rendered image drives generation:** eliminated for both preview and sync. Resolver only normalizes `metadata.attributes` (`lib/domain/searing/searing-layer-resolver.ts:66-75`) and materialization passes only `character.metadata` into it (`lib/services/searing-materialization-service.ts:439-442`). `metadata.image` is only used later for infected-image preservation/read-model display decisions (`lib/repositories/character-materialization-repository.ts:71-87`, `lib/repositories/character-materialization-repository.ts:145-151`).
- **`searImage` or a prior materialized image is composited into the next sear:** eliminated. Those fields appear in display candidate ordering and read-model updates (`lib/utils/image.ts:175-194`; `lib/repositories/character-materialization-repository.ts:107-121`), while composition inputs remain `resolution.layers` (`lib/services/searing-materialization-service.ts:439-445`). Completed event URLs can short-circuit status handling, but are not layer inputs (`lib/services/searing-materialization-service.ts:190-244`).
- **Searing materialization mutates root NFT traits:** eliminated. Resolver mutates only a local `workingAttributes` array for placeholder/missing layers (`lib/domain/searing/searing-layer-resolver.ts:172-179`), and the read-model update preserves existing root metadata while adding top-level searing fields (`lib/repositories/character-materialization-repository.ts:97-121`).
- **Normal sheet or AI persona edits update root `metadata.attributes`:** eliminated. Normal sheet PATCH allow-list excludes metadata/image fields (`lib/api/handlers/character-update.ts:26-31`, `lib/api/handlers/character-update.ts:95-110`); AI routes write Eliza character records, not `wagdie_characters` (`app/api/eliza/characters/[tokenId]/route.ts:151-218`; `app/api/eliza/characters/[tokenId]/import/route.ts:122-138`).

#### Concrete recommendations
1. If searing should reflect user-updated artwork, add an explicit generation path that can compose from a rendered/current source image or regenerate layer traits from that image. Current code is layer-based and cannot infer visual changes from `image_url`/`metadata.image`.
2. If searing should reflect edited traits, define and implement a canonical writer for root `metadata.attributes` (or a separate `current_traits` field) and update `resolveSearingLayersForCharacter` call sites to use that canonical trait source.
3. Add regression tests for preview and materialization that include conflicting `metadata.attributes`, `metadata.image`, `image_url`, `metadata.searImage`, and `metadata.searing_materialization.seared_image_url`, proving only the intended trait source affects `resolution.layers`.
4. Add tests around `updateSearingReadModel()` proving root `metadata.attributes` are preserved unchanged while `image`, `searImage`, `searing_materialization`, and `image_url` update as intended.
5. In UI copy/admin tooling, distinguish “display image” from “generation traits/source layers” so updated images shown by `getCharacterImageDisclosure()` are not assumed to affect searing composition.

## Investigation Log

### Phase 1 - Initial Assessment
**Hypothesis:** Searing preview/materialization may resolve layers from static/original token metadata, or from a stale character read model, rather than from the user-updated character metadata/image fields.
**Findings:** Likely areas include `app/api/characters/[tokenId]/searing/preview/route.ts`, `lib/services/searing-materialization-service.ts`, `lib/domain/searing/searing-layer-resolver.ts`, image composition/storage services, and character metadata update/read paths.
**Evidence:** Initial search found the preview endpoint calls `resolveSearingLayersForCharacter(character.metadata, concord)` and `searingImageComposer.compose(...)`.
**Conclusion:** Confirmed root-cause class after context builder, pair investigation, and oracle synthesis: generation is DB-backed but trait/layer-based; edited/display image fields are not composition inputs.

### Phase 4 - Oracle Synthesis
**Hypothesis:** The apparent use of original metadata is either a direct static metadata-file read, stale root DB trait attributes, or frontend cache/display ordering.
**Findings:** Oracle synthesis agreed the best statement is stale/original root DB `metadata.attributes` relative to edited/display images. Active preview/materialization paths read DB metadata, not `public/metadata/characters/*.json`; frontend display/caching can confuse what users see, but does not control backend composition.
**Evidence:** Preview selects `token_id, metadata` and composes `resolution.layers` (`app/api/characters/[tokenId]/searing/preview/route.ts:41-66`); resolver normalizes only attributes (`lib/domain/searing/searing-layer-resolver.ts:66-75`) and builds layer URLs (`lib/domain/searing/searing-layer-resolver.ts:160-216`); materialization resolves layers from `character.metadata` before any read-model update (`lib/services/searing-materialization-service.ts:428-445`); read-model update preserves existing root metadata via spread and adds searing display fields (`lib/repositories/character-materialization-repository.ts:97-121`); character PATCH allow-list excludes metadata/image fields (`lib/api/handlers/character-update.ts:26-31`, `lib/api/handlers/character-update.ts:95-110`).
**Conclusion:** Direct static metadata-file use and frontend cache are eliminated as primary generation causes. The remaining caveat is token-specific: if a failing token's `metadata.attributes` were truly updated before searing, inspect `searing_events.materialization_metadata.layers`, preview headers, and layer PNG availability.

## Root Cause
Searing image generation is trait/layer based, not rendered-image based. Preview and materialization both pass `character.metadata` into `resolveSearingLayersForCharacter()`, whose only character-art source is `metadata.attributes`; the composer then composites the resolved static layer PNGs. Runtime character sheet edits, AI persona edits, DB `image_url`, `metadata.image`, `metadata.searImage`, and previous materialized image URLs are display/read-model concerns and do not affect composition.

This means the system is usually not directly reading original static JSON files during searing. Instead, the DB row's root `metadata.attributes` often remains the original NFT trait set, so generation behaves as though it is using original metadata.

## Recommendations
1. Decide product intent: trait-driven searing, rendered-image-driven searing, or explicit hybrid source selection.
2. If trait-driven searing is intended, create a canonical editable trait source (`metadata.attributes` or a separate `current_traits`) and ensure edits that should affect searing update that source and have corresponding layer PNGs.
3. If current/displayed artwork should be the base, extend the resolver/composer/materialization path to accept a base rendered image (`image_url`, prior seared URL, or another explicit source) and overlay the searing layer onto it.
4. If sears should stack visually, persist the post-sear trait state or compose from the previous seared image; today `updateSearingReadModel()` preserves root attributes.
5. Add regression tests with conflicting `metadata.attributes`, `metadata.image`, `image_url`, `metadata.searImage`, and `metadata.searing_materialization.seared_image_url` to lock the intended source behavior.

## Preventive Measures
- Add UI/admin copy that distinguishes “display image” from “generation traits/source layers.”
- Persist source audit metadata with each sear: source type, trait snapshot or source URL, resolved layers, concord variant, and output URL.
- Add tests for `updateSearingReadModel()` proving root attributes are preserved or intentionally updated, depending on the chosen product direction.
- For token-specific reports, compare the DB row's `metadata.attributes` against `image_url`/display fields and inspect `searing_events.materialization_metadata.layers` before diagnosing cache or static-file issues.
