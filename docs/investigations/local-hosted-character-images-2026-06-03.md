# Investigation: Local Hosted Character Images and Seared Image Correctness

## Summary
The system currently has two separate image contracts that are not fully aligned: runtime character APIs use DB/read-model state plus dynamic image priority, while the NFT metadata route reads static JSON/local fallback only. Local file existence is also treated as proof of correctness in the asset pipeline, which caused token 30's stale local PNG problem; seared materialization currently writes GCS URLs in code, while production token 4702 shows local relative seared URLs from an unformalized rewrite/import path.

## Symptoms
- Character 30 demonstrated that a locally hosted PNG can differ from the canonical image referenced by metadata/IPFS.
- The app and NFT metadata routes need reliable local image hosting without serving stale or mismatched local files.
- Seared characters require special handling so their dynamic/seared image is local and preferred where appropriate.

### 2026-06-03 - Source-of-truth, route-policy, and local-hosting guarantee trace

#### 1. Source-of-truth candidates and route consumers
- **Static metadata snapshot:** `public/metadata/characters/{tokenId}.json` is loaded through `public/metadata/characters/manifest.json`, not directly from chain/IPFS at runtime. `characterLocalAssets` reads `public/metadata/characters/manifest.json` (`lib/services/assets/character-local-assets.ts:28`, `lib/services/assets/character-local-assets.ts:173-182`) and then reads each `metadata_file` listed in the manifest (`lib/services/assets/character-local-assets.ts:185-207`). This static snapshot is also the only source used by the NFT metadata endpoint (`app/api/characters/metadata/[tokenId]/route.ts:61-67`).
- **Static local image files:** `public/images/characters/{tokenId}.png` is treated as available by generated status code, not by per-request filesystem checks in the app image utility. Current status says no tokens are missing (`lib/data/local-character-asset-status.ts:1-11`), and `getCharacterImageCandidates()` therefore adds `/images/characters/{tokenId}.png` for every valid token after dynamic infected/seared candidates (`lib/utils/image.ts:194-216`). The manifest currently records 6,666 rows and only `image_exists`, `image_downloaded`, `image_source_url`, and errors; it has no hash/provenance fields (`public/metadata/characters/manifest.json:1-25`).
- **DB character read model:** `/api/characters` and `/api/characters/{tokenId}` use Supabase `wagdie_characters` via `getCharacters()`/`getCharacter()` (`lib/services/character-service.ts:19-33`) and `CharacterQueryRepository`, then hydrate each row through `runtimeAssets.hydrateCharacters()`/`hydrateCharacter()` (`lib/repositories/character/character-query-repository.ts:313-316`, `lib/repositories/character/character-query-repository.ts:385-388`, `lib/repositories/character/character-query-repository.ts:438-445`). Hydration starts from static local metadata, merges dynamic DB keys (`isSeared`, `searImage`, infection fields, `searing_materialization`, etc.), and recomputes `image_url` with display policy (`lib/services/assets/character-local-assets.ts:31-39`, `lib/services/assets/character-local-assets.ts:252-270`).
- **Searing event read model:** `/api/characters/{tokenId}/searing` reads `searing_events` through `activityRepository.findSearingEvents()` and returns DB rows, including materialization columns if selected by `*` (`app/api/characters/[tokenId]/searing/route.ts:40-47`, `lib/repositories/activity-repository.ts:92-108`). The materialization repository type confirms `searing_events.seared_image_url` and `materialization_metadata` are part of that row (`lib/repositories/searing-event-repository.ts:8-23`).
- **Generated seared-image source:** searing generation is layer-based: materialization resolves layers from hydrated character metadata and a concord map, composes them, uploads the resulting PNG, then stores the resulting URL in DB (`lib/services/searing-materialization-service.ts:423-458`). The preview route performs the same hydration and layer resolution but returns a PNG response without writing storage/read-model state (`app/api/characters/[tokenId]/searing/preview/route.ts:46-83`).
- **Token 4702 static-vs-runtime split:** local static metadata for token 4702 still points to IPFS and has no searing read-model fields (`public/metadata/characters/4702.json:2-4`, `public/metadata/characters/4702.json:45-57`), while production runtime JSON in the background section reports local-relative seared fields. This proves static JSON alone cannot be the current seared source for 4702.

#### 2. Download/import/rewrite scripts and unsafe defaults
- **`collect-character-assets.ts` writes static snapshots but does not verify existing bytes.** It writes DB `metadata` to `public/metadata/characters/{id}.json`, then if a local image exists and the row is not currently infected/seared, it records the file as present and returns without download or comparison (`scripts/collect-character-assets.ts:455-476`). There is no SHA-256, content length, canonical CID/source, or provenance in `ManifestEntry` (`scripts/collect-character-assets.ts:21-29`), so local file existence is treated as correctness.
- **Collector seared candidate order differs from runtime.** Runtime display prefers `metadata.searing_materialization.seared_image_url`, then `metadata.searImage`, then DB `image_url` (`lib/utils/image.ts:156-181`). The collector builds candidates as infected, `metadata.searImage`, nested `searing_materialization.seared_image_url`, then `image_url`/metadata image fields (`scripts/collect-character-assets.ts:224-234`). A stale legacy `searImage` can therefore win during refresh even when a newer materialization URL exists.
- **Collector can mark existing dynamic images missing after failed refresh.** For infected or seared rows, `shouldRefreshCurrentImage()` forces download (`scripts/collect-character-assets.ts:205-211`). If the download fails, `hasUsableLocalImage` excludes a previously existing local image when refresh was required (`scripts/collect-character-assets.ts:491-493`), so the manifest/status can mark an existing file unusable instead of retaining it with a verification failure.
- **`point-images-to-local.ts` only rewrites `metadata.image` and skips most existing rows by default.** It scans `public/images/characters`, builds `/images/characters/{file}` paths, loads DB `metadata`, and updates `metadata.image` plus `asset_import` (`scripts/point-images-to-local.ts:40-51`, `scripts/point-images-to-local.ts:108-133`). Its default `LOCAL_IMAGE_SKIP_EXISTING=true` skips rows with any non-empty existing `metadata.image` (`scripts/point-images-to-local.ts:18`, `scripts/point-images-to-local.ts:120-123`), and it does not update DB `image_url`, `metadata.searImage`, `metadata.searing_materialization.seared_image_url`, or `searing_events.seared_image_url`.
- **`import-gcs-images.ts` downloads GCS images locally but keeps DB URLs pointed at GCS.** It defaults to bucket `seared-wagdie-images` and download dir `public/images/characters` (`scripts/import-gcs-images.ts:22-24`), downloads matching bucket objects into `public/images/characters/{tokenId}.{ext}` (`scripts/import-gcs-images.ts:145-151`), but merges/updates `metadata.image` and `image_url` with the original GCS URL, not the local path (`scripts/import-gcs-images.ts:155-179`, `scripts/import-gcs-images.ts:294-321`). This cannot by itself explain production `/images/characters/4702.png?v=seared-...` fields.
- **Materialization can run from two paths, both using the same GCS-returning storage service.** Public per-character sync calls `verifyTransactionAndMaterialize()` (`app/api/characters/[tokenId]/searing/sync/route.ts:38-55`), and bulk/admin sync calls `materializePendingBatch()` behind `SYNC_SECRET_KEY` (`app/api/sync/searing/route.ts:22-29`, `app/api/sync/searing/route.ts:78-90`). The CLI `scripts/materialize-searing-events.ts` loops `materializePendingBatch()` with optional token scoping/retry (`scripts/materialize-searing-events.ts:37-75`). None of these paths localize the returned image URL.
- **OpenSea refresh is downstream invalidation only.** `refresh-opensea-metadata.ts` chooses token IDs from args or the static manifest and posts to OpenSea refresh endpoints (`scripts/refresh-opensea-metadata.ts:20-27`, `scripts/refresh-opensea-metadata.ts:126-153`, `scripts/refresh-opensea-metadata.ts:203-220`). It does not verify image bytes, materialize seared images, or rewrite app/database image fields.

#### 3. Searing materialization storage/read-model flow does not guarantee app-origin URLs
- The selected storage implementation is explicitly GCS. `SearingStorageService` defaults bucket name from `SEARING_GCS_BUCKET`/`GCS_BUCKET_NAME`/`GCS_BUCKET` or `seared-wagdie-images`, builds token/version object paths, and returns `https://storage.googleapis.com/{bucket}/{object}` (`lib/services/searing-storage.ts:58-70`). `uploadSearedImage()` saves with immutable cache headers and returns that public GCS URL (`lib/services/searing-storage.ts:74-93`).
- `SearingMaterializationService` generates a version from tx hash, log index, and image digest (`lib/services/searing-materialization-service.ts:90-93`), composes the image, calls `storage.uploadSearedImage()`, and stores the returned `searedImageUrl` (`lib/services/searing-materialization-service.ts:449-458`).
- The returned storage URL is written to **both** character and event read models. `updateSearingReadModel()` writes `metadata.image` unless infected image preservation applies, always writes `metadata.searImage`, `metadata.searing_materialization.seared_image_url`, and usually `image_url` (`lib/repositories/character-materialization-repository.ts:103-121`, `lib/repositories/character-materialization-repository.ts:164-178`). `markCompleted()` writes `searing_events.seared_image_url` (`lib/repositories/searing-event-repository.ts:202-221`).
- Existing unit tests encode GCS as the current expected behavior: materialization returns `https://storage.googleapis.com/seared-wagdie-images/...` (`tests/unit/searing-materialization-service.test.ts:103-120`), materialization metadata completion uses a GCS URL (`tests/unit/searing-materialization-service.test.ts:188-199`), and storage URL construction is tested as `https://storage.googleapis.com/...` (`tests/unit/searing-storage.test.ts:20-23`).
- Therefore, production token 4702's local-relative seared URL (`/images/characters/4702.png?v=seared-4b5906ec-log479`) is not emitted by current materialization code. It likely came from a separate/manual production rewrite, a one-off import/deploy process, or an untracked job. Current source cannot guarantee future seared events become local/app-origin URLs.

#### 4. Route/display policy divergence and exact fix points
- **Runtime API/display policy:** `getCharacterImageCandidates()` documents and implements: infected dynamic image, then seared dynamic image, then local downloaded/static asset, then placeholder (`lib/utils/image.ts:194-216`). Seared candidates are materialization URL, legacy `searImage`, then DB `image_url`, and only then metadata image fields if materialized candidates exist (`lib/utils/image.ts:156-181`). Because `/api/characters` and `/api/characters/{tokenId}` hydrate rows through this utility, runtime display can prefer DB seared fields over local static base images.
- **NFT metadata policy:** `/api/characters/metadata/{tokenId}` reads only static JSON, preserves any non-empty `metadata.image`, and falls back to hosted local PNG only when that static field is blank/missing (`app/api/characters/metadata/[tokenId]/route.ts:61-79`). It does not read Supabase, `searing_events`, `metadata.searImage`, or nested materialization fields, and it deletes only `animation_url` before returning (`app/api/characters/metadata/[tokenId]/route.ts:81-88`). Tests explicitly assert this preservation behavior even when a local PNG exists (`tests/api/characters-metadata-route.test.ts:37-53`).
- **Product decision A: NFT metadata should remain immutable/base.** Then keep `/api/characters/metadata/{tokenId}` static, but do not use it to validate current/seared display. Make this explicit in docs and monitoring: base metadata can show original/IPFS or hosted base image, while `/api/characters/{tokenId}` is current/seared display. Fix only the guarantee wording and collector verification for base images.
- **Product decision B: NFT metadata should expose current/seared art.** Fix `app/api/characters/metadata/[tokenId]/route.ts` to read the same hydrated character/read model as `/api/characters/{tokenId}` or at least consult DB/searing fields before static `metadata.image`; update `tests/api/characters-metadata-route.test.ts:37-91` to expect seared materialization precedence; decide whether returned image should be absolute app-origin local URL (`https://fateofwagdie.com/images/characters/{id}.png?v=seared-...`) rather than relative.
- **Product decision C: all app-visible character images must be local/app-origin.** Fix the storage/read-model path, not just display fallback. Either replace/extend `SearingStorageService` with a local/app-origin materializer that writes `public/images/characters/{tokenId}.png` (or a versioned local object path) and returns `/images/characters/{tokenId}.png?v=seared-{tx/log/hash}`, or add a mandatory post-upload localizer that downloads/writes the seared bytes and rewrites all three DB fields plus `searing_events.seared_image_url`. Also update `collect-character-assets.ts` to use runtime's seared candidate order and to verify hashes before accepting existing bytes.

#### 5. Test and monitoring gaps
- **No direct tests for `collect-character-assets.ts`.** Existing tests cover the image utility and some routes, but no test exercises skip-existing behavior, manifest hash/provenance, seared candidate order, failed refresh semantics, or `local-character-asset-status.ts` generation.
- **Metadata route tests currently enforce divergence.** `tests/api/characters-metadata-route.test.ts` covers preserving a non-empty static image and fallback only when missing/blank (`tests/api/characters-metadata-route.test.ts:37-91`), but has no seared/materialization scenario and no assertion that returned images are app-origin/local.
- **`/api/characters/{tokenId}` lacks GET route-level image-policy coverage.** The repository/service hydration path is covered indirectly, but there is no route test proving a seared DB row returns local/app-origin URLs or that static local fallback does not mask bad seared state. The only direct image-policy tests allow external GCS seared URLs (`tests/unit/image.test.ts:25-37`, `tests/unit/image.test.ts:77-86`).
- **Searing materialization tests would fail a local-only policy until updated.** Current service/storage tests expect GCS URLs (`tests/unit/searing-materialization-service.test.ts:103-120`, `tests/unit/searing-storage.test.ts:20-23`). Add policy tests that assert returned/stored seared URLs are app-origin local when that is the product requirement.
- **Ops monitoring needed:** add a scheduled audit that samples or scans all 6,666 tokens and all completed searing events for: local image file exists; local file hash matches manifest/canonical source; `metadata.image`, `image_url`, `metadata.searImage`, `metadata.searing_materialization.seared_image_url`, and `searing_events.seared_image_url` are consistent with policy; no `storage.googleapis.com`, IPFS, or `seadn.io` URLs remain in app-visible fields when local-only mode is enabled; completed searing rows have a fetchable local image and version query; NFT metadata route and runtime route either intentionally match or intentionally diverge according to the product decision.

#### Concrete recommendations
1. **Base image verification:** extend `collect-character-assets.ts` manifest entries with `sha256`, `byte_length`, `content_type`, `source_url`, `source_kind` (IPFS/GCS/OpenSea/local), and `verified_at`; when a local file exists, verify it against canonical metadata/IPFS or a stored expected hash instead of skipping blindly (`scripts/collect-character-assets.ts:455-476`). Fail/report mismatches like token 30 instead of treating local presence as success.
2. **Seared local materialization:** introduce a first-class seared local storage service or localizer that writes the composed PNG to app-hosted storage and returns the exact URL policy. Wire it into `SearingMaterializationService` before `updateSearingReadModel()` and `markCompleted()` (`lib/services/searing-materialization-service.ts:449-485`) so DB/event rows never temporarily rely on GCS if local-only is mandatory.
3. **Read-model repair script:** add an idempotent repair command for existing completed sears: fetch `searing_events.seared_image_url`/GCS if needed, write local PNG, compute version/hash, update `searing_events.seared_image_url`, `wagdie_characters.image_url`, `metadata.searImage`, and `metadata.searing_materialization.seared_image_url` together. Neither `import-gcs-images.ts` nor `point-images-to-local.ts` currently rewrites all of these fields (`scripts/import-gcs-images.ts:155-179`, `scripts/point-images-to-local.ts:108-133`).
4. **Metadata route decision:** choose immutable/base vs current/seared NFT metadata. If current/seared, make `/api/characters/metadata/{tokenId}` consult hydrated DB/searing state before static JSON and add seared route tests. If immutable/base, update docs/ops dashboards so route divergence is expected and not mistaken for a seared-image bug.
5. **Regression coverage:** add tests for collector skip-existing mismatch, manifest hash/provenance, seared candidate order matching `lib/utils/image.ts`, searing local storage URL policy, `/api/characters/{tokenId}` seared local response, `/api/characters/metadata/{tokenId}` chosen policy, and an ops audit fixture that fails on external app-visible URLs.
6. **Monitoring/alerts:** deploy a cron/CI report after asset collection and after searing materialization that emits counts of missing local files, hash mismatches, external image URLs in app-visible DB fields, completed searing rows without local image, and metadata/runtime divergence. Alert on non-zero counts for local-only policy violations.

## Root Cause
1. **Local file existence is treated as correctness.** `scripts/collect-character-assets.ts` records already-present non-infected/non-seared images as valid without comparing bytes against the canonical metadata/IPFS/DB source, and the manifest lacks hash/provenance fields. Token 30 proves this is unsafe: its local PNG exists but differs from the canonical metadata/IPFS image.
2. **Image routes use different source contracts.** `/api/characters/{tokenId}` reads DB rows, merges dynamic seared/infected metadata, and resolves images via runtime priority. `/api/characters/metadata/{tokenId}` reads static JSON only, optionally uses local fallback, deletes `animation_url`, and does not consult DB `image_url`, `metadata.searImage`, `metadata.searing_materialization.seared_image_url`, or `searing_events`.
3. **Searing materialization does not guarantee app-origin/local URLs in selected code.** `SearingStorageService` uploads to GCS and returns `https://storage.googleapis.com/...`; `SearingMaterializationService` writes that returned URL into character and event read models. Production token 4702's `/images/characters/4702.png?v=seared-...` URL is not produced by the selected materializer, so future sears are not guaranteed to become local/app-origin without a formal localizer/proxy/storage change.
4. **Searing indexing and materialization are separate.** Indexing can record events without generating or repairing images. A reliable worker/cron/repair path is required to ensure every seared event has a correct image.
5. **Collector and runtime seared priority diverge.** Runtime prefers `searing_materialization.seared_image_url` before `searImage`, while the collector tries `searImage` first. The collector can therefore refresh/localize stale legacy seared images.

## Confirmed and Eliminated Hypotheses
- **Confirmed:** token 30's regression came from trusting a stale local PNG and treating local existence as enough.
- **Confirmed:** the current manifest cannot prove local image correctness because it lacks hash/provenance/verification data.
- **Confirmed:** runtime display can prefer DB seared fields, but NFT metadata route cannot because it does not read DB/searing state.
- **Confirmed:** selected searing storage code emits GCS URLs, not local/app-origin URLs.
- **Eliminated:** static `30.json` directly contains the bad local URL; it contains the IPFS image.
- **Eliminated:** middleware explains `/images/characters/30.png`; middleware excludes `/images`.
- **Eliminated:** searing indexer alone should generate seared art; materialization is separate.
- **Unsupported:** current selected code explains production token 4702's local relative seared URL; that appears to be production state drift, a manual repair, or a separate untracked rewrite/import path.

## Product Policy Decisions Required
1. **NFT metadata meaning:** decide whether `/api/characters/metadata/{id}` should be immutable/base NFT metadata or current dynamic/seared metadata. If immutable/base, token 4702-style metadata/runtime divergence is expected and should be documented. If current/seared, the route must read DB/hydrated read-model state and return current seared image/traits.
2. **Meaning of “hosted locally”:** decide whether only app-origin URLs such as `/images/characters/{id}.png?v=...` qualify, or whether controlled GCS storage is acceptable. If app-origin only, materialization/storage must stop writing app-visible GCS URLs or must proxy/localize them before DB writes.
3. **Canonical base source:** decide whether base art truth is static metadata `image`, DB `metadata.image`, DB `image_url`, marketplace cache, or verified local manifest. Token 30 shows local files cannot be canonical by default.

## Recommendations
1. **P0 — Preserve token 30 safety.** Do not reintroduce blanket hosted-image overrides. A valid canonical metadata image must not be displaced by an unverified local file.
2. **P0 — Add verified base-image audit/localization.** Extend asset collection so existing local images are compared against canonical source bytes before being accepted. Manifest entries should include `canonical_source_url`, `canonical_source_kind`, `local_file`, `local_sha256`, `source_sha256`, `byte_length`, `content_type`, `verified_at`, `verification_status`, and `mismatch_reason`.
3. **P0 — Formalize seared local storage.** If app-origin local URLs are mandatory, add a first-class seared local storage/localizer path before `updateSearingReadModel()` and `markCompleted()`: compose image, write/copy to app-hosted storage, compute version/hash, and store the same local URL in `wagdie_characters.image_url`, `metadata.searImage`, `metadata.searing_materialization.seared_image_url`, and `searing_events.seared_image_url`.
4. **P1 — Add repair tooling for existing sears.** Create an idempotent command that scans completed searing events, verifies URL policy, fetches legacy GCS/local source if needed, writes verified local/app-origin image, and updates event plus character read-model fields together.
5. **P1 — Align collector with runtime priority.** Make `collect-character-assets.ts` use the same seared order as `lib/utils/image.ts`: `searing_materialization.seared_image_url`, then `searImage`, then DB `image_url`, then fallback candidates. Do not mark existing dynamic images as missing when refresh fails; mark them stale/unverified/refresh_failed.
6. **P1 — Decide metadata route policy and test it.** If metadata is current/seared, change `/api/characters/metadata/{id}` to read hydrated DB state and return absolute marketplace-safe local URLs. If metadata is immutable/base, document divergence and ensure base local fallback is verified only.
7. **P1 — Operationalize materialization.** Ensure a scheduled worker/cron processes pending/failed/stale searing events, supports repair for legacy rows, alerts on failures, and triggers marketplace refreshes when metadata/image URLs change.

## Preventive Measures
- Add regression tests for token 30-style local/canonical mismatch, asset collector skip-existing verification, manifest hash/provenance output, seared candidate order, searing storage URL policy, and metadata route behavior for both base and seared fixtures.
- Add monitoring reports for missing local files, hash mismatches, manifest entries without source proof, external image URLs in app-visible DB fields under local-only policy, completed searing events without policy-compliant image URLs, failed/stale materialization rows, and metadata/runtime route divergence.
- Treat `public/images/characters/{id}.png` as a cache/mirror, not source of truth, until verified.
- Keep route/display contracts explicit in docs: immutable/base metadata vs current app display vs seared materialization are different unless intentionally unified.
- Require CDN and marketplace cache refresh as part of any image URL or image-byte repair operation.
